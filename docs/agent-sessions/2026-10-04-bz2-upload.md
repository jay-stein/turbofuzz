# 2026-10-04 — bzip2 (.bz2) upload support

## Problem

`GlobalLandTemperaturesByCity.csv.bz2` was fed to the CSV parser as raw
binary, producing garbled output: the loader had no bzip2 handling (only
zip/gz), and unknown compressed files weren't rejected either.

## What was added

- `.bz2` accepted by the dropzone, file picker and URL loader.
- `src/parse/bz2.ts`: lazy pure-JS decoder (SheetJS `bz2`, 5.9KB separate
  chunk) using a small adapter because the package exposes itself via
  `window.bz2` in browsers and `module.exports` in Node.
- `openBzip2` decompresses on the main thread, yielding once so the
  "Decompressing bzip2…" status paints, then routes the inner file through the
  existing gz/zip/workbook/data paths (`routeDecompressed`).
- Unsupported compressions (.xz, .zst, .7z, .rar, .tar, .lz4) now show
  "try .zip, .gz or .bz2" instead of garbling.

## WASM exploration (rejected)

- `@foxglove/wasm-bz2` decoded the real 508MB output in 11s (vs 135s pure JS)
  but Vite 8/rolldown cannot bundle its emscripten CJS `require("...wasm")`
  (REQUIRE_TLA error) in either the app or worker bundles.
- `bzip2-wasm` has the same dest-size requirement plus a broken Windows Node
  path, and `seek-bzip` is Node-only (Buffer/stream).

## Performance note

Pure JS runs ~3.8MB/s of output. The test file (49MB compressed → 508MB,
8.6M rows) takes ~2.2 minutes and is at the edge of browser memory; ordinary
bz2 CSV files (a few MB) decompress in a second or two. Zip/gz remain much
faster for large uploads.

## Verification

107 tests (bz2 fixture decode), typecheck and production build clean; main
bundle unchanged, decoder is a lazy chunk.
